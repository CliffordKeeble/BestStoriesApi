# Measurements of 10 October 2026

Everything `docs/performance.md` quotes, how it was taken, and where the raw output is. A number here that has no raw file beside it says so.

## The machines

**The VM (every table unless stated).**
- A shared cloud VM under KVM: 2 vCPUs (Intel Xeon), 7 GB RAM, Ubuntu 24.04, .NET 10.0.12, Release builds.
- The VM reports 2 cores with 1 thread each. Whether the host maps them to sibling hyperthreads of one physical core cannot be seen from inside.
- **Placement.** The API ran on one core (`taskset -c 1`). The load generator and the fake Hacker News shared the other (`taskset -c 0`), and requests went over loopback.
- **Read every figure as one core of a small shared VM.** A dedicated machine will do better in absolute terms. Absolute figures also drift over the evening on a shared VM, so only same-session, interleaved comparisons are quoted.

**A laptop (where stated).**
- AMD Ryzen 5 PRO 7535U (6 cores, 12 threads), Windows 11, .NET 10.0.12.
- **Conditions.** On battery, Balanced power plan, no core pinning.
- **Who measured it.** A separate run from a clean clone, by a second operator. Its raw logs stayed on that machine; the figures below are as that operator reported them.

## Latency and throughput: `2026-10-10-interleaved.csv`

Produced by `bench/wrk2-suite.sh` and summarised by `bench/summarise.py`. Every run's full output is in `2026-10-10-interleaved/`, under the name in the CSV's `raw` column.

**Method.**
- **Builds.** Two builds ran side by side: the first commit on port 5029, the current one on port 5028, both on the API core.
- **Interleaving.** The builds alternated run by run: before, after and the empty-404 floor, three rounds per scenario. A noisy minute on the shared VM therefore lands on both builds, not on one.
- **Open loop.** `wrk2 -t1 -c64 -d15s -R<rate> --latency`. wrk2 sends at a fixed rate and corrects for coordinated omission, so a stall is charged to every request that queued behind it.
- **Closed loop.** `wrk -t1 -c64 -d10s`.
- **Rejection.** A run that achieved less than 98% of its target rate is marked `valid=0` and left out of the median. It is still counted, and its raw file is still there.
- **What was rejected.** Two runs, both of the current build: n=200 at 2,000/s achieved 1,866.75, and n=200 at 5,000/s achieved 4,666.32. Each is 93.3% of its target. The first run of the day had the same shortfall at the same scenario on the old build, so it is likely wrk2's own per-connection pacing at that rate (64 connections). The rejection rule takes it out, whatever its cause.

**How to read it.**
- **The floor is mostly the load generator's.**
  - An empty 404 from the same server has a median of 1.05–1.19 ms, and the current build sits within about 0.1 ms of it.
  - The same .NET client was then run twice at 2,000/s, changing only how it waits between sends:

    | | spins | sleeps 1 ms |
    |---|---:|---:|
    | the endpoint, n=10: median | 0.163 ms | 0.986 ms |
    | an empty 404: median | 0.167 ms | 0.946 ms |

    The raw output is in `2026-10-10-interleaved/loadtest_*.txt`.
  - So about 0.8 ms of the ~1.1 ms is the time between a request falling due and the client sending it, not the server.
  - Those four runs fail the tool's own validity check (1% of sends more than 1 ms late), because on this 2-core VM the client had to share the server's core. Only their medians are used here.
  - wrk2 probably adds the same kind of delay, from scheduling its sends on a millisecond timer. That is a reading, not a measurement.
- **The gain grows with the size of the answer and the load.**
  - n=10 at 2,000/s: the median falls by 0.18 ms (1.28 to 1.10).
  - n=200 at 7,500/s: p99 falls from 32 ms to 3.3 ms. At that rate the old build was at 71% of its closed-loop maximum (7,500 / 10,589).
- **Tails above p99 are noisy on a shared VM:** one run of 18 ms becomes a p99.9 of 113 ms. That is why the median of three is shown, and the range beside it.
- **Refreshes were not excluded.** The API refreshes once a minute, so about one 15-second run in four contains a refresh. Some tail outliers may be that.
- **The n=10 maximum may be the generator's limit.** On the current build it is 44,100/s, close to the ~44,600/s that the same generator reached for empty 304s in the first run. So it may be what wrk on one core can send, not what the endpoint can serve.

## Allocation per request: `2026-10-10-interleaved/alloc_*.csv`

**Method.**
- `dotnet-counters collect` sampled the counter `dotnet.gc.heap.total_allocated` (bytes per second) once a second for 20 s, while wrk2 sent 5,000 requests/s.
- Bytes per request = the mean of the busiest 18 samples, divided by 5,000.
- The figure includes everything the process allocated in those seconds: at most one background refresh, and the counters' own overhead. Both are small next to 100,000 requests.

| | n = 10 | n = 200 |
|---|---:|---:|
| before (the first commit) | 13,838 bytes | 14,256 bytes |
| after | 3,839 bytes | 3,900 bytes |
| an empty 404, same server | 3,175 bytes | |

After the change, the endpoint's own share is about 660–725 bytes per request: query parsing, headers and the response flush. It is much the same whatever n is. The rest is what ASP.NET Core spends on any request.

## Conditional requests: `2026-10-10-interleaved/etag_*.txt`

**Method.**
- Score changes in the fake were switched off (`Fake__ChangesPerMinute=0`), so the answer's tag held still.
- `wrk -c64 -d10s` alternated full answers and requests sending the tag in `If-None-Match`, three rounds each.

| n | full answers | 304s | bytes on the wire |
|---:|---:|---:|---:|
| 200 | 17,847–20,150/s | 28,226–36,495/s | about 570 MB/s → about 4.4 MB/s |
| 10 | 30,800–32,676/s | 32,206–34,971/s | about 52 MB/s → about 4.6 MB/s |

**Running order.** These ran later in the evening, on a separately started server, and the VM was slower by then. So only the alternated ratio is quoted: about 1.65× the responses for n=200, at about a hundredth of the bytes.

**What 304s are worth to a client.**
- The snapshot changes at most once a minute. A client polling faster than that gets 304 for every poll except the first after a refresh that changed its answer.
- A client polling slower than once a minute rarely gets one, because live Hacker News scores move every minute.

## Upstream calls under load: `2026-10-10-interleaved/upstream_load*`

The fake's call counters (`/stats`, raw JSON kept) were read over two minutes at each caller load, with n = 10 and wrk2 at a fixed rate:

| caller load | requests served | calls to Hacker News |
|---:|---:|---:|
| none | 0 | 402: 2 refreshes of 1 id list and 200 items |
| 5,000/s | about 599,000 | 402 |
| 20,000/s | about 2,397,000 | 402 |

**The bound is per refresh, not per caller.**
- It is 201 calls a refresh, whatever the callers do. Callers cannot raise it.
- Hacker News's own failures can raise it. The standard resilience handler retries a failed call up to 3 times, so a bad minute can cost up to four times as many calls.

## The laptop's load tests (as reported)

**Valid:** the closed loop (LoadTest, 64 connections).
- n=10: 57,800/s before, 69,900–74,700/s after.
- n=200: 21,090/s before, 43,180–43,420/s after (about 2.05×).

**Not valid:** every open-loop row.
- On Windows, `Thread.Sleep(1)` sleeps about 15.6 ms, and the generator of that day slept between sends. So it could not keep a schedule, and it marked every row invalid.
- The generator now measures its sleep at start and spins on a coarse timer. With a 16 ms tick simulated on the VM (`LOADTEST_SIMULATE_TICK_MS=16`) and the client given two cores at 5,000/s:
  - the old waiting gave a send delay of 16.2 ms at p99 and a latency median of 11.1 ms;
  - the new pacing gave 0.85 ms and 0.105 ms.
- Those two runs were read from the console and not kept as files.
- The rerun with the fixed generator, on 11 October, is in [`2026-10-11-laptop.md`](2026-10-11-laptop.md).

## The first run of the day: `2026-10-10-first-run/`

**What it was.** The builds were measured an hour apart, not interleaved, and runs that fell short of their rate were kept.

**Why it is superseded.**
- An independent review found its "before" n=200 at 2,000/s row was built from two short runs.
- That run's "before" build reached 8,750/s against 10,589/s in the interleaved run, so it had less headroom. Its 7,500/s row therefore showed a p99 of 264 ms where the interleaved run shows 32 ms.

It is kept so the change is visible, not quoted.
