# Measurements of 10 October 2026

Everything the README's performance section quotes, with how it was taken. The raw runs are the CSV files beside this one.

## The machine, and what that means for the numbers

- A shared cloud VM: 2 vCPUs (Intel Xeon @ 2.10 GHz), 7 GB RAM, Ubuntu 24.04, .NET 10.0.12 runtime, Release builds.
- The API was pinned to one core (`taskset -c 1`). The load generator and the fake Hacker News shared the other (`taskset -c 0`). So every figure here is **one core of a small VM**: a laptop or server will do better in absolute terms.
- Load and server were on the same machine, over loopback.
- The tail varies from run to run on a shared VM: in identical runs p99 ranged from 3 ms to 98 ms. That is why every scenario was run three times and the median is reported with the spread. The before and after builds were measured the same way on the same machine, an hour apart.

## What was measured

| file | code |
|---|---|
| `2026-10-10-before-4ee5907.csv` | the API as first committed (`4ee5907`): MVC controller, serialise per request |
| `2026-10-10-step-a-minimal-endpoint.csv` | a minimal endpoint in place of the controller, still serialising per request (source-generated JSON) |
| `2026-10-10-after.csv` | the snapshot serialised once per refresh, each answer a slice of it, ETag and 304 |

**Open loop:** `wrk2 -t1 -c64 -d15s -R<rate> --latency`, after an 8 s warm-up. wrk2 sends at a fixed rate and corrects for coordinated omission, so a stall is charged to every request that queued behind it.
**Closed loop (max throughput):** `wrk -t1 -c64 -d10s`.
The script is `bench/wrk2-suite.sh`.

## The floor of this machine

An empty 404 from the same server, same settings: median **1.04 to 1.12 ms** at 2,000/s and **1.27 to 1.32 ms** at 7,500/s (two runs each). After the change the endpoint's median sits on that floor at every rate measured. What is left at the median is the VM and the loopback, not the code.

## Allocation per request

`dotnet-counters collect`, counter `dotnet.gc.heap.total_allocated`, at 5,000 requests/s for 20 s:

| | n = 10 | n = 200 |
|---|---:|---:|
| before (`4ee5907`) | 14,126 bytes | 16,390 bytes |
| after | 3,792 bytes | 3,807 bytes |
| an empty 404, same server | 3,178 bytes | |

After the change the figure no longer depends on n: the serialisation is gone from the request path. About 600 bytes are the endpoint's own; the rest is what ASP.NET Core spends on any request.

## Conditional requests

Score changes in the fake were switched off so the tags held still. n = 200, closed loop: **about 22,000 responses/s at roughly 640 MB/s** for full answers, against **about 44,600/s at 6 MB/s** when the client sent its ETag back and got 304. n = 10: no change in throughput, because the body was small to begin with. At 7,500/s the latency of a 304 is the machine's floor.
